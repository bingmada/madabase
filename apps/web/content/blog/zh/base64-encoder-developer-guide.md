# Base64 Encoder 开发者使用指南

Base64 encoder 会把字节转换成更容易在文本系统中传递的表示形式，适合小型调试、Data URL、基础传输格式和文档示例。Base64 不会让数据变得私密，任何拿到编码结果的人通常都可以把它解码回来。

## Base64 实际做了什么

Base64 会把输入字节分组，再映射到有限字符表。标准字符表包含大小写字母、数字、`+` 和 `/`，末尾可能出现表示补位的 `=`。Base64URL 版本会用 `-` 和 `_` 替代部分字符，更适合 URL 和某些 token 格式。编码后的文本通常比原始字节更长，因此它不是压缩。

例如，文本 `hello` 编码后是 `aGVsbG8=`。结果看上去不容易阅读，但其中没有加密密钥，也没有提供安全保护。它只是数据的一种表示形式，不是安全边界。

## 如何选择合适的流程

对于短小且不敏感的内容，可以使用 [Base64 Encoder 工具](/zh/tools/base64-encoder) 快速转换。编码前先确认输入是文本还是二进制，并确认目标系统采用哪一种字符编码。文本通常使用 UTF-8，但不同系统可能按照其他方式解释字节。

解码时，先判断数据使用的是哪一种变体。URL 或 JWT 中的值可能使用 Base64URL，而不是标准 Base64。Base64URL 有时会省略末尾补位，接收库会自动恢复。如果解码出现奇怪字符，应检查原始字符编码、换行和空格、是否复制了额外前缀，以及 URL 百分号编码是否还没有还原。

## 开发中常见的用途

Basic Authentication 经常把 `username:password` 的 Base64 表示放进请求头。它只是编码，所以请求仍然需要 HTTPS，凭证也必须按照秘密信息管理。Data URL 可以在 HTML 和 CSS 中嵌入小图片或字体，但大文件会让页面更慢，也更难利用缓存。文档示例可以使用 Base64 fixture，但应该使用虚构数据。

JWT 的片段使用 Base64URL 编码，而不是加密。即使没有签名密钥，解码器也可能显示其中的 header 和 payload。因此，不要因为 payload 被编码，就把密码、secret 或客户隐私放进去。

## 输出异常时怎么排查

如果结果不可读，先确认输入本来是不是文本。PNG、压缩文件或加密后的字节，解码后不一定会变成可读文字。再检查是否混入多余空格、复制了前缀、补位错误，或把 Base64 与 Base64URL 混用。比较两个值时，必要时比较解码后的字节或稳定 hash，不要因为补位方式不同就认定它们一定是不同数据。

## 隐私与大小限制

不要把生产凭证、access token、私钥、客户记录或支付数据粘贴到在线 encoder。敏感数据应使用本地或经过批准的环境。还要记住，编码通常会让数据体积增加大约三分之一，之后 JSON 转义和传输还可能继续增加长度。除非已经测量过性能影响，否则 Data URL 和内嵌 payload 应保持小巧。

## 最后总结

Base64 解决的是传输和表示问题，不是加密、压缩、认证或访问控制。使用前确认变体和字符编码，并始终保护原始数据。
