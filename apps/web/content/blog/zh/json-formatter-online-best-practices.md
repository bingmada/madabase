# JSON Formatter Online 使用指南与调试技巧

JSON formatter online 最适合放在一个完整的审查流程中使用。它可以把一行接口响应转换成便于人工检查的树状结构，但不能判断响应是否符合你的业务要求。更稳妥的方式是把格式化、语法校验、脱敏和接口契约检查结合起来。

## 格式化、校验和 schema 检查不是一回事

格式化只改变空格和换行，让对象和数组更容易阅读。语法校验会检查引号、逗号、大括号、方括号以及 JSON 支持的值类型。schema 检查则更进一步，它会判断必填字段是否存在、数字是否在范围内、字段类型是否符合约定。

例如，下面的内容在语法上是有效 JSON，但对某些应用来说仍然可能是错误响应：

`{"status":"ok","items":null}`

如果客户端约定 `items` 始终是数组，格式化器无法发现这个业务层面的不一致。你需要把预期结构写入接口契约或测试，再将格式化后的结果与契约逐项比较。

## 一套适合浏览器的工作流

1. 只复制能复现问题的最小响应，内容越小越容易检查，也越安全。
2. 打开 [JSON Formatter 工具](/zh/tools/json-formatter)，粘贴响应内容。
3. 执行格式化，并在工具提供相应选项时进行语法校验。
4. 展开报错字段附近的对象或数组，检查字段类型、拼写和嵌套层级。
5. 与同一接口的正常响应进行比较，确认问题是请求、环境还是数据本身。
6. 在工单或测试夹具中保存脱敏后的示例，不要保存生产原始响应。

这套流程适合 webhook body、REST 响应、GraphQL variables、配置快照和小型事件消息。如果内容是超大导出文件、二进制数据，或包含注释和模板表达式的“类 JSON”文本，在线格式化器不一定是最佳选择。

## 如何进行有价值的比较

两个 payload 可能因为键顺序和空白不同而看起来不同，但实际值完全一致。比较前先统一格式，然后重点查看状态码、标识符、缺失值与 null 的区别、数组长度和嵌套错误详情。还要特别留意字符串形式的数字，例如 `"100"` 和 `100`，很多客户端对它们的处理不同。

如果接口返回很长的列表，可以先比较一个代表性元素和分页元数据。缺少 `nextCursor`、分页大小变化，或空数组，都可能解释客户端问题，不必把整份响应放进工单。

## 隐私与安全检查

不要把 access token、Cookie、密码、私钥、支付数据或未脱敏的客户记录粘贴到在线工具或公开问题中。脱敏时尽量保留真正影响问题的数据形状。JWT 可以保留三段结构但换成虚构 token；邮箱可以改成 `person@example.test`；内部 URL 可以保留路径形状并替换域名。

## 最后总结

在线 JSON formatter 的价值是让结构变得可见，而不是替你做判断。先校验语法，再对照契约，分享前完成脱敏；对于敏感或超大的 payload，应使用本地工具或经过批准的数据处理流程。
