# 如何格式化 JSON

格式化 JSON 不只是给内容增加换行。一个可靠的格式化流程，可以帮助你看清 API 响应的层级、找到导致测试失败的字段，并在不改变数据本身的前提下分享可读的示例。格式化器应该只调整空格和换行，不应该悄悄改变键名、值、数组顺序或数据类型。

## 先了解有效 JSON 的规则

很多格式化错误都可以用下面几条规则解释：

- 对象的键和值使用双引号，键和值之间用冒号分隔。
- 数组使用方括号，可以包含对象、字符串、数字、布尔值或 null。
- 字符串必须使用双引号。单引号在 JavaScript 源码中可能出现，但不是有效 JSON。
- 最后一个对象属性或数组元素后面不能有多余逗号。
- JSON 不支持注释、`undefined`、`NaN` 和 `Infinity`。

例如，下面是一段有效的紧凑 JSON：

`{"user":{"id":42,"roles":["editor","reviewer"]},"active":true}`

格式化后，嵌套关系会更加清楚，`roles` 数组也更容易检查。如果工具提示错误位置，不要只看那个字符。真正的问题可能是前面几位缺少引号或逗号，解析器通常只能报告它最终无法继续的位置。

## 一套可复用的格式化流程

1. 如果输入来自日志，先去掉 `Response:`、时间戳、日志前缀或 Markdown 代码围栏，确保剩下的是纯 JSON。
2. 将内容粘贴到 [JSON Formatter 工具](/zh/tools/json-formatter) 中并执行格式化。
3. 在把结果放入测试、工单或文档前，再进行一次语法校验。
4. 分享前检查 access token、邮箱、内部域名和客户编号等敏感字段。
5. 如果你在排查数据变化，可以比较格式化后的版本，避免变更藏在一整行文本中。

格式化和校验不是一回事。格式化器可以让有效文档变得可读，但不能判断接口返回的业务值是否正确，也不能判断接口是否缺少契约要求的字段。

## 常见调试场景

当 API 客户端提示收到的不是合法 JSON 时，先确认服务器返回的是否真的是 JSON。有时实际响应是 HTML 错误页、代理层提示或空响应。再检查响应编码和第一个非空白字符：对象通常以 `{` 开始，数组通常以 `[` 开始。如果同一请求在不同环境表现不同，应比较实际响应正文，而不是只看请求代码是否相同。

配置文件适合在每次小修改后格式化并查看相邻对象。这样不仅能发现少一个或多一个大括号，也能帮助你发现看起来重复的键。不同解析器对重复键的处理方式可能不同，因此不要依赖重复键的行为。

## 分享数据前的隐私检查

不要把生产环境密钥直接粘贴到公开工单或截图中。可以保留相同的数据类型进行脱敏，例如把 `"token":"真实值"` 改成 `"token":"REDACTED"`，把真实用户编号改成测试编号。保留能够说明问题的层级，删除与问题无关的记录。如果数据包含个人信息，优先重新构造一份虚拟示例。

## 最后总结

用格式化器理解结构，用校验器确认语法，再用 API 契约或 schema 判断数据是否符合业务要求。把这三个步骤分开，JSON 调试会更快，也能避免把“看起来整齐”误认为“已经验证正确”。
